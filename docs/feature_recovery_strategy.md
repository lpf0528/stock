# InStock 缺失功能恢复策略与实施方案

更新日期：2026-08-08

## 1. 结论与调整原则

当前系统不应再以“完整量化平台”作为默认对外承诺。数据库中可稳定使用的是综合选股和部分事件/资金流数据；股票/ETF 行情、指标、K 线形态、策略和回测链路均没有可验证产物。

恢复策略从“按原有全量每日任务反复重跑”调整为：**先使数据可验证，再恢复计算，最后开放展示与自动化**。任何下游结果都必须绑定其输入交易日、数据量和运行状态；空表、旧缓存或失败任务不得显示为成功。

> 运行状态的唯一事实来源仍是 `docs/database_capability_context.md`。本文件定义恢复路线，不替代运行快照。

## 2. 已确认的缺口

| 优先级 | 缺失或失效能力 | 已知证据 | 用户影响 |
| --- | --- | --- | --- |
| P0 | 每日行情与 ETF 行情 | `cn_stock_spot`、`cn_etf_spot` 不存在 | 无法得到可用于计算的当日全市场股票池 |
| P0 | 每日任务编排 | `execute_daily_job.py` 当前只运行初始化和数据抓取；没有调用指标、形态、策略、回测作业 | 即使行情恢复，后置结果也不会自动产出 |
| P0 | 指标、买卖信号、K 线形态、策略、回测 | 对应表不存在，快照无数据 | 菜单中存在的功能页面只能返回空列表 |
| P1 | 数据新鲜度与失败可见性 | Web 在表缺失或查询异常时直接返回 `[]` | 用户无法区分“没有结果”和“任务失败/未初始化” |
| P1 | 基础表初始化覆盖范围 | 初始化目前只显式补齐关注与部分资金流表 | 下游表继续依赖首次成功写入而隐式建表，失败时无可诊断结构 |
| P1 | 可重复验证 | 仓库没有自动化测试目录；作业没有统一的完成清单 | 修复后难以判断是否真正恢复 |
| P2 | 实盘自动交易 | 上游选股和回测不可用，且交易依赖 Windows 券商客户端 | 不具备安全启用条件 |

## 3. 目标状态与边界

第一阶段目标是恢复“日终研究链路”，不是恢复实盘交易：

```text
可验证行情快照
  -> 指标与买卖信号
  -> K线形态与策略选股
  -> 回测填充
  -> Web 状态化展示
```

每个箭头都需要前一环节通过门禁。ETF 行情仅作为独立展示和后续 ETF 分析的输入；本轮不把 ETF 强行并入现有股票指标/策略逻辑。自动交易保持关闭，必须在策略可复现、回测口径确认及人工风控验收后另立项目评估。

## 4. 分阶段实施方案

### 阶段 A：建立运行门禁与观测（P0）

1. 增加统一的作业状态记录：作业名、目标交易日、开始/结束时间、输入/输出行数、状态、错误摘要、版本号。
2. 为关键表定义最小数据契约：表存在、目标交易日存在、行数阈值合理、代码去重率正常。阈值应配置化，不能把某日固定行数写死。
3. 每个作业成功后执行契约校验；失败则标记 `failed` 或 `degraded`，阻断依赖作业。不得用历史缓存冒充目标日期的新数据。
4. 增加只读的健康检查命令，输出“可运行/阻断原因/建议操作”，供 Cron、部署和 Web 共用。

验收：在行情缺失时，执行入口明确报告被阻断的下游作业；不创建或覆盖当天的指标、策略、回测结果。

### 阶段 B：恢复并固化行情输入（P0）

1. 将东财 `push2` 的 Chrome 指纹 + 有效 Cookie 传输层保留为主实现，并抽象为可替换数据源接口；Cookie 仅从本地未跟踪配置读取，绝不写入日志或提交。
2. 增加备用来源/导入适配器，并统一输出同一行情数据契约。备用来源的选择需单独确认授权、频率、复权口径与数据延迟。
3. 初始化改为显式、幂等地创建全部日终链路所需表；建表与写数据分离，避免“抓取失败导致表不存在”。
4. 先用一个交易日完成股票与 ETF 行情定向补数，再验证代码数、日期、主键唯一性和字段完整性；通过后才开放批量补数。

验收：`cn_stock_spot` 与 `cn_etf_spot` 均存在，最近交易日有可信数据；重复执行同一日期不会产生重复记录；源不可用时保留上一份数据并明确标为过期。

### 阶段 C：按依赖顺序恢复计算链路（P0）

1. 恢复指标作业，先以单日小样本验证，再全市场执行；验证技术指标非空比例、买卖信号规则和异常代码清单。
2. 恢复 K 线形态和 11 个策略作业；每个策略独立记录候选数、异常数和版本，避免一个策略失败中断其余策略。
3. 最后运行回测。回测只处理拥有足够后续交易日的数据，并明确标注“待填充”与“无有效样本”，不能把未成熟样本算入胜率。
4. 修订 `execute_daily_job.py` 为显式 DAG：初始化 -> 行情门禁 -> 其它基础数据（可并行） -> 指标 -> 形态/策略（可并行） -> 回测。每一步只在依赖契约通过后调度。

验收：选择一个已补足历史窗口的交易日，所有目标表有同日期产物；回测的统计样本数可追溯到具体选股记录；任一上游失败时下游不会运行。

### 阶段 D：Web 与运维收口（P1）

1. 将 API 的空数组语义拆分为：`empty`（确无结果）、`not_ready`（表/日期缺失）、`stale`（非最新交易日）、`failed`（任务失败）。页面展示更新时间、数据来源、行数和阻断原因。
2. 菜单仅在功能满足最低数据契约时显示为可用；不可用功能保留入口但显示恢复状态与操作建议，避免误导。
3. Cron 只触发统一编排入口，并在失败时保留结构化日志和告警；不要由小时任务与日终任务并发写同一目标日期。
4. 补充单元测试（日期门禁、幂等写入、失败阻断）和一个接入测试（使用脱敏/固定行情样本走完整 DAG）。

验收：用户能从页面和健康检查中看出每项功能的可用状态；一次失败可定位到数据源、表、交易日和作业步骤。

## 5. 发布顺序与回滚

1. 先发布阶段 A 的状态与门禁，不自动启动后置计算。
2. 完成阶段 B 单日验收后，开启阶段 C 的单日计算；确认后再补历史和接入每日调度。
3. 阶段 D 随每个能力恢复同步上线，避免 Web 状态落后于实际数据。
4. 新作业版本必须支持按“作业 + 交易日”重跑。失败回滚采用停调度、保留旧结果和运行记录的方式；不删除历史数据，只有确认目标日期错误时才做定向替换。

## 6. 当前建议的执行优先级

| 顺序 | 工作项 | 前置条件 | 产出 |
| ---: | --- | --- | --- |
| 1 | 作业状态表、数据契约、健康检查 | 无 | 所有缺失功能可被准确诊断 |
| 2 | 全量表初始化与行情来源可替换化 | 1 | 可验证的股票/ETF 日行情 |
| 3 | 单日指标恢复 | 2 | 指标及买卖信号表 |
| 4 | 单日形态、策略、回测恢复 | 3 且历史窗口足够 | 可追溯的研究结果 |
| 5 | DAG 编排、历史补数、Cron | 2-4 全部验收 | 稳定的每日自动产出 |
| 6 | Web 状态化、测试与告警 | 1-5 逐步完成 | 可运营、可解释的系统 |
| 7 | 实盘交易评估 | 1-6 稳定运行一段观察期 | 单独的风控与授权决策 |

## 7. 明确不应采取的做法

- 不要在 `push2` 失败时反复重跑整套每日任务，尤其不要因旧缓存写入而把结果标为当天数据。
- 不要仅凭表结构、页面菜单或无异常日志判断功能可用；必须检查目标交易日、行数和数据契约。
- 不要在阶段 C 之前重新启用全量策略、回测或自动交易。
- 不要提交或记录东方财富 Cookie、代理凭据、券商账号和密码。
